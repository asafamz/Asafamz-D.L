# Asafamz Digital Library

A custom Whop Experience View + Dashboard View that replaces the missing Files/Content workflow for Asafamz digital products.

## What it does

- Customer-facing gated digital library inside Whop.
- Admin dashboard for ASAFAMZ team members.
- Creates/attaches an Experience to a selected Whop product.
- Uploads PDFs directly to Whop's private file storage using a presigned URL.
- Stores the private file ID in the Whop product metadata.
- Retrieves a fresh signed URL only after Whop access is verified.
- Supports the first cookbook and can be reused for future ebooks.

## Whop Hosting

- Base URL: your deployed HTTPS URL
- Experience path: `/experiences/[experienceId]`
- Dashboard path: `/dashboard/[companyId]`
- Discover path: `/discover`

These match Whop's current Next.js app template and documentation.

## Required environment variables

`NEXT_PUBLIC_WHOP_APP_ID`

`WHOP_API_KEY`

`WHOP_WEBHOOK_SECRET` (optional unless webhooks are added)

## Required Whop permissions

The app needs the permissions corresponding to the API operations it performs, including product read/update, experience create/attach, and file creation/retrieval. Whop requires permissions to be requested, saved, and approved when the app is installed.

## Deployment

Whop's official Next.js template recommends deploying the app to Vercel, adding the environment variables there, and then placing the production URL in the Whop Developer Dashboard Hosting > Base URL. The same template uses `/experiences/[experienceId]` and `/dashboard/[companyId]`.

## Setup flow

1. Create/deploy this Next.js app.
2. Set the Whop environment variables on the hosting provider.
3. Put the production URL into Whop > Developer > Asafamz Digital Library > Hosting > Base URL.
4. Keep the Experience path `/experiences/[experienceId]`.
5. Keep the Dashboard path `/dashboard/[companyId]`.
6. Request/approve the required app permissions and install the app into ASAFAMZ.
7. Open the app's Dashboard View.
8. Find `Pure Taste: Swahili Coast Kitchen — 31 Authentic Recipes`.
9. Click `Create library` if an experience has not already been created.
10. Upload the finished cookbook PDF. The app stores it privately and connects it to the product.
11. Open the customer Experience View and test with a customer account.

## Security

Never put `WHOP_API_KEY` in client-side code. The browser only receives a presigned upload URL generated by the server. Customer PDF URLs are private, signed URLs that expire. Whop's documentation recommends private visibility for sensitive or paid content.

## Why some calls use raw REST instead of `@whop/sdk`

`@whop/sdk` is intentionally pinned at `0.0.3`. That version's TypeScript types:

- have no `files` namespace at all,
- don't know about `is_public` on `experiences.create`, and
- don't correctly model `metadata` on `products.update`.

Rather than upgrade the SDK (which would require re-verifying every other call
site against a much newer API surface), `lib/whop-rest.ts` implements a small,
fully typed `fetch`-based client for exactly those three operations: file
upload/retrieval, experience creation, and product metadata updates. Every
other call — user auth (`verifyUserToken`) and access checks (`checkAccess`) —
still goes through `lib/whop-sdk.ts` / `lib/whop-access.ts`, since 0.0.3 has
always handled those correctly.

If you later upgrade `@whop/sdk`, `lib/whop-rest.ts` can be retired and its
callers pointed back at `whopsdk.files` / `whopsdk.experiences.create` /
`whopsdk.products.update` — but confirm those methods' current type
signatures first, since the underlying API has moved on since 0.0.3 was
published (some resources now accept `account_id` alongside `company_id`).
